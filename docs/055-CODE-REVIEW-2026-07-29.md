**Author:** Chief Architect
**Scope:** 220 JS files, 23 pages, 67 test suites.
**Result:** one latent defect found and fixed; three checks came back clean; two
latent risks recorded and deliberately not fixed.
**Severity of the fix:** S2 — a silent, permanent stop of the component that feeds the

Automated checks first, each chosen because it can find a *real* defect rather than

## 2. The defect: a collector that dies on one bad cycle

All three warehouse helpers ended the same way:

```js
run();
if (every) setInterval(run, every * 1000);
```

No `.catch()` on either call, and no `unhandledRejection` handler in any of the three
files.

**Verified, not assumed:** node v24.14.1 terminates the process on an unhandled
rejection. A probe was run to confirm it on the node actually in use.

So one rejected cycle ends the helper. The two synchronous ones — `option-warehouse`
(mirror) and `warehouse-derive` — are worse rather than better: they do file I/O, so a
torn JSON file or a disk error throws straight out of the timer callback.

**Why it matters more than it looks.** Nothing would restart it. The launcher runs at
logon and at 08:50 (docs/053, `7623b70`); there is no supervisor between. The bot would
keep running, the dashboard would keep serving, and the warehouse would simply stop
filling — with no error anywhere a person looks. That is the same shape as the morning
that went missing on 2026-07-29, and the warehouse is the input to a hero-zero base
rate that is *already* blocked on data (docs/051).

**Latent, not active.** 653 lines of capture log carry no unhandled rejection, and
`jget()` catches its own network errors, so the likely paths are covered. This was
fixed anyway because the consequence is a silent permanent stop and the fix is six
lines — not because it was firing.

### The fix

`loop-guard.js` — `runLoop(name, task, everyMs)`. It:

- runs the first cycle immediately, exactly as before;
- catches both rejections and synchronous throws;
- **logs every failure with its message** — the error is surfaced, not swallowed;
- escalates on a run of consecutive failures, because *a loop that fails forever in
  silence is worse than one that stops: a stopped process is at least visible in a
  process list*;
- announces recovery, so a loop that was failing and now is not does not look
  identical to one that never failed;
- logs nothing at all while healthy.

**Demonstrated side by side**, same poisoned task, 400 ms:

| | still alive | failures logged |
|---|---|---|
| old shape | **no — dead on the first cycle** | 0 |
| guarded | yes | 6 |

## 3. Clean results worth recording

**Cross-module contracts: 0 violations across 71 modules.** Every `mod.fn()` call
resolves to something that module actually exports.

**Import-time side effects: not a live problem.** 16 root modules do work when merely
required — all of them `bt-*` backtests, `postmortem`, `preflight`. None has a
`require.main === module` guard, so importing one runs a 600-day backtest. **None is
imported by anything**, so the risk is latent. Left alone rather than fixed, on the
same principle as docs/054: no defect, no change.

**Syntax: clean across 220 files.**

## 4. A pattern worth naming

Four times now, a test in this codebase has matched **prose instead of code** and
reported the opposite of the truth — most recently here, where the guard's own comment
quotes the `setInterval(run, …)` it removed, and quoting the defect you fixed is the
normal way to document it.

`test/loop-guard.test.js` now strips comments in one helper that every shape assertion
goes through. **Any assertion about code shape must read code, not comments.** The
same rule already had to be learned in `signal-heatmap-ui`, `ui-shell` and
`opt-at-low`.

## 5. An accident, and what it accidentally proved

The import-time side-effect scan in §1 *required* every root module to read its
exports. Sixteen of them run work on import — so the scan **ran the backtests**, which
rewrote their result files. Those files were then swept into commit `19e3b18`, whose
message says nothing about them. Recording that here rather than rewriting pushed
history.

It is worth stating plainly: **a tool that reads a codebase should not be able to
execute it.** The scan was moved to a child process per file for exactly this reason,
but only after the damage. That the backtests have no `require.main === module` guard
(§3) is what made a read into a run.

The accident did answer a question nobody had asked: **is `bt-real` reproducible?**

`result-real.json` came back with 435 of 470 rows differing, which looks alarming.
Field by field, only **four trades** changed economically; the other 431 were the
running capital compounding those four.

| # | Date | Change |
|---|---|---|
| 35 | 2024-03-13 | entry **5.7 → 38.7**, exit 5.3 → 36 |
| 124 | 2024-09-12 | entry **0.9 → 27.5**, exit 0.9 → 25.6 |
| 194 | 2025-01-24 | pnl −686 → −800 |
| 320 | 2025-09-16 | pnl −659 → −672 |

And the headline conclusions:

| Metric | Committed | Regenerated |
|---|---|---|
| Trades | 470 | 470 |
| Win rate | 6.8 % | 6.8 % |
| Profit factor | 2.041 | **2.042** |
| Net | ₹345,524 | ₹345,623 |

**The conclusion does not move.** The backtest is reproducible in every sense that
matters, and the ₹99 difference comes from four trades whose *input data* was
corrected when the bhavcopy cache filled in.

**One observation worth someone's attention, not fixed here:** entries of **₹0.90** and
**₹5.70** were previously accepted and later corrected to ₹27.50 and ₹38.70. A
thirty-fold correction is not a rounding difference — those were bad or missing rows
that the harness priced anyway. The strategy has a `MAXPREM` filter but evidently no
floor that would have refused a 90-paise entry as implausible. Under the project's own
`null ≠ 0` rule, a missing price should have been unknown rather than cheap. That is a
research-integrity question for `bt-real.js`, and it is recorded rather than acted on
because the outcome it produced was immaterial.

## 6. What this review did not find

No memory growth, no failing health checks, no silent catch firing on any exercised
path (docs/054), no contract violations, no syntax errors, and — after `381f6d2` — no
rate-limit refusals under load.

The honest summary is that the codebase is in good shape, and the remaining items are
**unknown rather than broken**: the hero-zero base rate needs 20 clean sessions and has
1, the forward test reads INSUFFICIENT at 22/30, and the live gate stands at 0/6. Those
need time and data, not code.
